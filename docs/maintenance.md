## 1. Паспортная часть и общие положения

### 1.1 Назначение документа

Регламент определяет состав, периодичность и порядок работ по поддержанию программы «polygon-tool» и её данных в работоспособном состоянии, а также зоны ответственности участников. Цели регламента:

- свести к минимуму простои и риск потери наборов точек координат;
- обеспечить целостность и восстановимость данных (резервное копирование, проверка копий, тестовое восстановление);
- обеспечить сохранение работоспособности и качества ПО при обновлении окружения (автотесты, обновление Python и зависимостей);
- обеспечить предсказуемые действия при сбоях (инцидентное ТО);
- обеспечить безопасность данных (контроль прав доступа, вынос копий на внешний носитель).

### 1.2 Область применения

| Объект ТО | Состав |
|---|---|
| Программное обеспечение | Программа «polygon-tool» версии 1.0.0 (модули `geometry`, `io_handlers`, `backup`, `cli`); интерпретатор Python 3.10+; dev-зависимости `pytest`, `pytest-cov` |
| Данные | Хранилище точек `data/points.json`; резервные копии и манифесты в `backups/` |
| Репозиторий и автоматизация | Репозиторий GitHub `Timofei12345-1/polygon-tool`, прогон тестов в GitHub Actions |
| Аппаратная часть | ПК или сервер с ОС Windows, Linux или macOS; диск с достаточным свободным местом; внешний носитель или сетевое хранилище для копий |

Регламент не распространяется на обслуживание операционной системы, сети и самого сервиса GitHub.

### 2.2 Внеплановое (инцидентное) ТО

#### Классификация инцидентов

| Приоритет | Признак | Срок начала работ |
|---|---|---|
| Критический | Потеряно или повреждено хранилище; нет пригодных копий | Немедленно |
| Высокий | Повреждена копия; не выполнено плановое копирование; программа не работает | В течение рабочего дня |
| Средний | Ошибки ввода и расчёта, красный статус автоматических тестов | В течение 3 рабочих дней |

Общий порядок: зафиксировать признаки и время инцидента → выполнить действия карты → убедиться в восстановлении работоспособности → при дефекте ПО завести задачу (Issue) в репозитории.

#### ИК-01. Повреждение или потеря хранилища

| Параметр | Содержание |
|---|---|
| Признак | Программа сообщает о некорректном JSON или об отсутствии файла `data/points.json` |
| Вид ТО | Внеплановое |
| Алгоритм | 1. Прекратить запись в хранилище.<br>2. Выполнить `python -m polygon_tool list-backups` и определить последнюю корректную копию.<br>3. Выполнить `python -m polygon_tool restore` (самая свежая копия; проверка целостности выполняется автоматически) либо `restore --file <копия>`.<br>4. Проверить данные: `python -m polygon_tool calc -i data/points.json`.<br>5. Выяснить причину (диск, права, внешнее вмешательство). |
| Ожидаемый результат | Хранилище восстановлено, расчёт выполняется; причина установлена |

#### ИК-02. Повреждённая резервная копия

| Параметр | Содержание |
|---|---|
| Признак | `verify` или `list-backups` сообщает «ОШИБКА» или «ПОВРЕЖДЕНА»; код возврата 3 |
| Вид ТО | Внеплановое |
| Алгоритм | 1. Не использовать повреждённую копию; переместить её в отдельный каталог для анализа.<br>2. Для восстановления выбрать более раннюю корректную копию (`restore --file`).<br>3. Создать новую копию: `python -m polygon_tool backup`.<br>4. Проверить остальные копии: `python -m polygon_tool verify`.<br>5. Найти причину (сбой носителя, копирование без проверки, ручное изменение файлов). |
| Ожидаемый результат | Есть свежая корректная копия; `verify` завершается кодом 0 |

#### ИК-03. Восстановлены не те данные

| Параметр | Содержание |
|---|---|
| Признак | После `restore` данные не соответствуют ожидаемым |
| Вид ТО | Внеплановое |

Откатиться: `restore --file <копия состояния до восстановления>`.<br>3. Выбрать верную копию по дате и количеству точек и повторить восстановление. |
| Ожидаемый результат | Хранилище содержит нужный набор точек |

#### ИК-04. Ошибка хранилища или копий (код 3)

| Параметр | Содержание |

Если данные корректны, а программа даёт неверный результат, — это дефект ПО: воспроизвести на минимальном примере, завести Issue, добавить тест, исправить, выполнить ТК-06. |

Исправить дефект в отдельной ветке (`fix/...`), добавить или скорректировать тест, выполнить ТК-06, слить через Pull Request. |

| Состояние | Условия |
|---|---|
| Норма | Все параметры контроля в пределах целевых значений |
| Требует внимания | Нарушен один некритичный параметр (например, свободное место, покрытие тестов) |
| Неисправность | Нет актуальной корректной копии; повреждено хранилище; тесты не проходят |

### 3.3 Порядок контроля и отчётность

Администратор ежемесячно проверяет значения параметров контроля и сообщает о результатах проверяющей: какие технологические карты выполнены, значения параметров, возникшие инциденты и принятые меры. Проверяющая раз в квартал оценивает выполнение регламента и при необходимости согласует его изменения. Изменения регламента вносятся через репозиторий (отдельный коммит `docs: ...`) с обновлением версии и даты документа.
